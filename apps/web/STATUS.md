## Homepage fix: "the web shows the old website"

The user's literal report was accurate but not a bug: `app/page.tsx` (the marketing/waitlist landing page) hadn't been touched since June 16, predating this entire build — visiting `/` always showed that unchanged page, correctly. The actual gap was that a signed-in user had no reason to ever land there again, and the navbar had no visible path into the real product at all (every CTA was waitlist-only). Fixed with two small, deliberately non-destructive changes: `/` now redirects a visitor with a session cookie straight to `/browse` (signed-out visitors still see the marketing page, unchanged — this isn't a rewrite of the marketing narrative, which is a content/brand decision outside this fix's scope), and the navbar gained a "Sign In" link. The waitlist form itself is untouched — `LAUNCH.md`'s pre-launch supply-seeding strategy still depends on it, so removing it wasn't this fix's call to make.

## Bug fixed this pass: Next.js dev-server crash in `tailwind.config.ts`

Hit live while restarting the dev server mid-session: `next dev` intermittently crashed with `ReferenceError: require is not defined` while compiling the `/` route, because `tailwind.config.ts` called the bare CJS `require("../../design-tokens")` at module scope — Next's dev-server config loader apparently doesn't deterministically choose CJS vs. ESM interpretation for a `.ts` config file in this monorepo layout, and `require` is only a global in the CJS case. Fixed by switching to a proper ESM `import tokensImport from "../../design-tokens"` (works correctly under either interpretation given `esModuleInterop`), plus a new co-located `../../design-tokens.d.ts` ambient type declaration so `tsc` (which has `allowJs: false`) can still type the import without needing to compile the `.js` file itself. `design-tokens.js` itself is untouched — `apps/mobile`'s plain-JS `tailwind.config.js` still `require()`s it directly with no issue, since Metro's bundler is unambiguously CJS. Confirmed fixed: several clean dev-server restarts afterward, no recurrence.

## Known gaps in what's built

- **Nothing has been opened in an actual browser.** Every check above is HTTP-level (curl against route handlers, `tsc --noEmit`, `next build`, and for chat a Node `socket.io-client` script standing in for a real browser tab). No hydration check, no visual check, no click-through of the actual React forms (photo picker, amenity toggles, OTP box auto-advance, the chat input/auto-scroll, etc.) — this is the same class of gap `apps/mobile`'s STATUS.md flags for its own UI (device/simulator never run).
- **Cloudinary upload is untested** — placeholder `NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME`/`_UPLOAD_PRESET` in `.env.local`, same as `apps/mobile`'s `.env.development`. The create-listing photo-upload path has never actually hit Cloudinary.
- **Editing a listing's photos still isn't built** — content-field editing shipped 2026-08-19 (`/listing/[id]/edit`), but photos are excluded on purpose: `apps/api`'s update endpoint doesn't touch `images` at all, only settable at create time.
- **No sort options or Map/List toggle on `/browse`** — both are documented `apps/mobile`+`apps/web` parity items in root `CLAUDE.md`'s Airbnb-level feature set, neither built on either surface yet.
- **Chat socket token never refreshes for a long-open tab** — same gap as `apps/mobile`'s `socket.ts`: `/api/chat/socket-token` is fetched once per `connectSocket()` call, so a chat tab left open past the 15-minute access-token window silently stops receiving real-time pushes until the page is reloaded/renavigated.
