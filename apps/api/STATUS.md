## Auth module (`src/auth/`) — built and verified against the live database

Endpoints: `POST /auth/google`, `POST /auth/otp/send`, `POST /auth/otp/verify`, `POST /auth/refresh`, `POST /auth/logout`, `GET /auth/me` (guarded), `PATCH /auth/onboarding` (guarded).

**Verified for real on 2026-08-18** (`nest start` against live `ghor-dev`, not just `nest build`): OTP send → dev-console code logged, never in the response → OTP verify creates a real `Profile` row and returns a token pair → `GET /auth/me` returns it with `idDocumentUrl` stripped → `PATCH /auth/onboarding` updates `fullName`/`role` → **attempting `role: "admin"` is rejected with a 400 at the DTO layer**, confirmed, not just reasoned about → `POST /auth/refresh` rotates the pair and **replaying the spent refresh token is rejected with 401**, confirmed. Google OAuth is built the same way but untested — no `GOOGLE_CLIENT_ID` configured yet, needs a real Google Cloud OAuth client to test against.

- **Google OAuth**: verified server-side via `google-auth-library`'s `OAuth2Client.verifyIdToken` (audience-checked against `GOOGLE_CLIENT_ID`) — never trusts a client-asserted identity.
- **Phone OTP**: 6-digit code, bcrypt-hashed at rest, 5-minute expiry, 5-attempt cap, 60-second resend cooldown. **Sending is stubbed**: if `SMS_API_URL` isn't set (true today — no credentials from the founder yet, root `CLAUDE.md` §5/§12), the code is logged server-side via `Logger.warn` instead of sent, and never returned in the API response. If `SMS_API_URL` *is* set, the service currently throws — the real HTTP call to the provider isn't implemented (no provider API shape to build against yet).
- **Tokens**: access (15m) + refresh (30d) JWTs, separate secrets. Refresh tokens are hashed with SHA-256 (not bcrypt — they're high-entropy, unlike the OTP code, so a fast deterministic hash is correct and is what makes the exact-match revocation lookup possible) and rotated on every use (old one revoked, new pair issued).
- **`phoneVerified`** is set true on successful OTP verify; **`lastActiveAt`** is touched inside `JwtStrategy.validate()` on every authenticated request (fire-and-forget, never blocks the request) — both trust-feature fields from §2 are now actually wired, not just schema.
- **`role` escalation to `admin`** is structurally blocked: `OnboardingDto`'s `@IsIn(['seeker', 'owner'])` means `admin` can never reach the service layer from this endpoint, not just "guarded by a check that could be forgotten."
- **`idDocumentUrl`** is stripped out of every `GET /auth/me` response, including the owner's own — per the sensitivity note in `CLAUDE.md` §6.
- **Bug found and fixed 2026-08-18: stale role claim after onboarding.** `PATCH /auth/onboarding` updates `Profile.role` in Postgres but the caller's *current* access token — minted at OTP-verify time, before onboarding ran — still carries the old JWT `role` claim (default `seeker`) until it naturally expires (15 min). Found live: a freshly-onboarded owner's `role` claim (decoded from a JWT obtained moments after onboarding) read `seeker`. Nothing in the listings or chat modules actually branches on the JWT's `role` claim today (ownership checks compare `ownerId`/`seekerId` against the authenticated user's `id`, not their role; the only role-based check anywhere is `role === 'admin'`, unreachable via onboarding), so this was latent, not a live functional bug — but it's exactly the kind of staleness that would matter the moment anything *does* branch on it. Fixed: `completeOnboarding()` now compares role before/after and calls `issueTokens()` to mint a fresh pair whenever the role actually changed, returning `{ profile, accessToken, refreshToken }` (`accessToken`/`refreshToken` are `null` when role didn't change — e.g. a seeker onboarding as a seeker). **This changed `PATCH /auth/onboarding`'s response shape** from a flat `Profile` to `{ profile, accessToken, refreshToken }` — both `apps/mobile/src/features/auth/api.ts` and `apps/web`'s new dedicated `app/api/auth/onboarding/route.ts` were updated to match and to save/cookie the reissued tokens when present.
- **Not yet built inside this module**: promoting a user to `admin` (no path exists yet — will need either a direct DB update by the founder or a future admin-module endpoint), account deletion (still lives with the admin/account module, not here), rate-limiting at the HTTP layer (only the OTP-specific attempt/cooldown counters exist, no general request throttling yet).

## Listings module (`src/listings/`, `src/institutions/`) — built and verified live

Endpoints: `POST /listings`, `GET /listings` (browse feed), `GET /listings/mine`, `GET /listings/:id`, `PATCH /listings/:id`, `DELETE /listings/:id`, `GET /institutions`. All guarded — root `CLAUDE.md` §2/§7.4 requires login before browsing on both surfaces, so there's no public listings route at all.

**Verified for real on 2026-08-18** (two separate live test accounts against `ghor-dev`, not just `nest build`): created a listing with 2 photos → attempted to publish → correctly rejected (400, "at least 3 photos required") → created a second listing with 3 photos → published (`draft` → `pending`) → confirmed it's invisible on the public browse feed but visible on `GET /listings/mine` → manually approved it (direct Prisma, simulating the not-yet-built admin action) → confirmed a **second** account now sees it on the browse feed, a `listing_view` event was recorded for that second account only (not for the owner's own views) → confirmed the draft listing is a 404 (not 403) to the second account → confirmed the second account gets 403 trying to edit the first account's listing → confirmed the owner **cannot** skip straight from `draft` to `approved` (403 — self-approval blocked) → confirmed the owner **can** mark their own approved listing `rented` and it disappears from the browse feed → confirmed `GET /institutions` returns `200 []` (table is real, just empty) → confirmed an unauthenticated request gets `401` → confirmed delete actually removes the row.

- **Draft → publish flow**: every `POST /listings` creates a `draft`, regardless of what the client sends — matches the schema comment ("force to pending" only fires on the owner's explicit publish, never on insert). Publishing is a `PATCH .../:id` with `{"status": "pending"}`, which is exactly where the 3-photo minimum is enforced (root `CLAUDE.md` §2/§6).
- **Status transitions resolve a real ambiguity in the spec**: root `CLAUDE.md` §4 says "owner can mark rented," §6 says "only admin can change status" — both are true, scoped to different transitions. Non-admins may only do `draft → pending` (publish) and `approved ↔ rented` (mark rented / available again); anything else (self-approving, un-rejecting, etc.) is a 403. Admins can set any status. This resolution is documented in code comments on `ListingsService.resolveStatusTransition()`, not just here.
- **Visibility**: `GET /listings/:id` returns 404 (not 403) for a listing that exists but isn't visible to the caller — doesn't confirm to a stranger that someone else's draft/pending/rejected listing exists.
- **View tracking**: a `listing_view` event is recorded on every non-owner detail fetch, fire-and-forget — the data source for the "X people viewed this today" trust signal (root `CLAUDE.md` §2), though nothing surfaces that aggregate back to a client yet (see Not started below).
- **Institutions**: `GET /institutions` supports `?search=` (type-ahead) and `?city=` (defaults to Guwahati). Read-only, matches the "no self-serve admin CRUD at MVP" decision (§2/§11). Filtering the browse feed by institution (`?institutionIds=a,b,c`) and tagging a listing on create/update (`institutionIds` in the body) both work — just untested beyond schema-shape, since **the table itself is still empty** (no seed data, same blocker as before this pass).
- **Not yet built inside/around this module**: geocoding (`latitude`/`longitude` stay null — no map provider chosen yet, `DESIGN.md` Known Gaps), editing photos on an existing listing (only settable at create time — `PATCH` doesn't touch `images` at all right now), sort by "most viewed" (only `newest`/`price_asc`/`price_desc` — most-viewed needs an events aggregation query not written yet), and any endpoint for admin approval itself (this pass simulated it with a raw Prisma call — the real thing is the admin module, still not started).

## Chat module (`src/chat/`) — built and verified live, REST and real-time both

Endpoints: `POST /conversations` (get-or-create), `GET /conversations` (list mine), `GET /conversations/:id/messages` (cursor-paginated), `POST /conversations/:id/messages` (REST fallback send). Socket.io gateway (`ChatGateway`, default namespace, no path change from `main.ts`'s HTTP server): `conversation:join`, `conversation:leave`, `message:send` → broadcasts `message:new` to everyone in `conversation:<id>`'s room. All guarded — REST via the existing `JwtAuthGuard`, the gateway via its own `handleConnection()` JWT verification (same `JWT_ACCESS_SECRET`, no separate secret).

**Verified for real on 2026-08-18**, three separate rounds:
1. **REST, two live test accounts**: seeker `POST /conversations` against a real listing → conversation created; re-posting the same `listingId` returns the *same* conversation (confirmed via `@@unique([listingId, seekerId])`) → owner attempting to start a conversation on their own listing → 400, blocked → seeker sends a message → owner's `GET /conversations` shows it with a correct `lastMessage` → owner replies → seeker's `GET /conversations/:id/messages` shows both, newest-first, cursor-paginated like the listings feed → a **third, unrelated** account gets 403 on both read and send → an unauthenticated request gets 401.
2. **Socket.io gateway, raw `socket.io-client` script**: both accounts connect with `auth: { token: accessToken }` → owner joins the conversation room → seeker emits `message:send` → owner's socket receives `message:new` in real time → a socket connecting with no token gets disconnected by `handleConnection()`. All passed.
3. **Socket.io gateway again, this time with `apps/web`'s actual token-issuance path**: fetched a token from `/api/chat/socket-token` (the new Next.js route that reads the httpOnly cookie server-side and hands back the underlying access token) for both a seeker and an owner session created entirely through `apps/web`'s BFF proxy, then ran the same connect → join → send → receive round trip using *those* tokens. Confirms the web client's actual auth path (cookie → server-side token fetch → Socket.io handshake) works end-to-end, not just a token obtained by curling `apps/api` directly.

- **Notifications**: `sendMessage()` fire-and-forget writes a `Notification` row (`type: 'new_message'`) for the recipient — the durable in-app record. **Push/email delivery on top of this is not built** — no `push_tokens` registration endpoint exists yet, no email module — so root `CLAUDE.md` §7.7's "owner must be pinged even with the app closed" requirement is only partially met (the row exists for a future in-app notification center to read, but nothing proactively reaches the recipient today).
- **Room-per-conversation**, not a global channel — `conversation:<id>`, matching root `CLAUDE.md` §14.5 exactly.
- **Token staleness on long-lived sockets**: the JWT is verified once at `handleConnection()`, never re-checked for the life of the socket. A connection made with a soon-to-expire access token stays open past that token's nominal expiry until the client disconnects/reconnects — same category of gap as the onboarding-role staleness above, and same reasoning for leaving it as a documented gap rather than building token-refresh-over-websocket right now (both client apps already reconnect with a fresh token on next mount/navigation, which bounds the exposure).
- **Not yet built**: read receipts (`Message.readAt` exists in the schema, nothing sets it), typing indicators, the "response rate/response time" trust signal that's supposed to be computed from this table (root `CLAUDE.md` §2 — pure read/aggregation, not blocked on anything here, just not written).

## Reports module (`src/reports/`) — built and verified live

Endpoints: `POST /reports` (any authenticated user), `GET /reports` (admin — open/`pending` reports only), `PATCH /reports/:id` (admin — `{action: 'dismiss'|'confirm'}`).

Replaces the old Postgres trigger (root `CLAUDE.md` §6's `reports` entry) with application logic in `ReportsService`: creating a report re-counts open reports on that listing and, if the count reaches `app_config['report_threshold']` (falls back to `3` if that config row doesn't exist) **and** the listing is currently `approved`, reverts it to `pending` — the same auto-revert-to-moderation-queue behavior the trigger used to provide. `PATCH .../:id` with `{action: 'confirm'}` is a separate, stronger path: an admin explicitly confirming a single report always forces the listing back to `pending` and marks the report `reviewed`, regardless of the threshold; `{action: 'dismiss'}` just marks it `dismissed` and leaves the listing alone.

**Verified for real on 2026-08-18**, with `report_threshold` deliberately set to `2` via the admin config endpoint to make the auto-revert path exercisable without creating many accounts: a first report on an `approved` listing left it `approved`; a second report (2/2) auto-reverted it to `pending`, confirmed by re-fetching the listing → a non-admin got 403 on `GET /reports` → the admin's open-reports queue showed both → dismissing the first report left the listing's state alone → confirming the second marked it `reviewed` and (redundantly, since it was already `pending`) forced `pending` again → the queue was empty afterward. Also confirmed a non-participant reading `GET /reports` before being admin-promoted got 403, matching the guard.

- **Bug found and fixed 2026-08-19, building the first client UI for this endpoint**: `create()` had no guard against a listing's own owner reporting it. Not exploitable against anyone else (self-only), but clearly wrong — the chat module's `getOrCreateConversation()` already has the analogous "can't act on your own listing" guard, this one just never got it. Fixed: `listing.ownerId === reporterId` now throws a 400 ("You cannot report your own listing"). Verified live: an owner's attempt to report their own approved listing was rejected after the fix (it had silently succeeded before it).
- **`apps/mobile` and `apps/web` both got their first Report-listing UI on 2026-08-19** — a category-chip + free-text dialog (`ReportDialog`) reachable from a small "Report" link on listing detail (non-owner view only). Verified live end-to-end through `apps/web`'s actual routes: a seeker's report landed in the admin queue, the owner's blocked self-report confirmed the new guard, and dismiss still worked as before.

## Admin module (`src/admin/`, plus `admin/*` routes on `ListingsController`) — built and verified live

Admin actions live with the feature they act on, not in one monolithic module: `GET /listings/admin/queue` (all `pending` listings, oldest first) and `POST /listings/admin/bulk-status` (`{ids, status: 'approved'|'rejected'}`) are on `ListingsController`; report resolution is on `ReportsController` (above); everything else that doesn't belong to an existing feature — users, config, analytics — is the new `AdminController` (`GET/PATCH /admin/users`, `GET/PATCH /admin/config`, `GET /admin/analytics`). All of it sits behind a new `AdminGuard` (`src/auth/admin.guard.ts`, checks `req.user.role === 'admin'`, always paired with `JwtAuthGuard`).

- **First-admin bootstrap — built 2026-08-18, but the first verification was incomplete; the real end-to-end path only actually works as of 2026-08-19.** A new `ADMIN_PHONES` env var (comma-separated E.164 numbers) is checked in `AuthService.promoteIfBootstrapAdmin()`, called from both `verifyOtp()` and `googleLogin()` right after the profile is resolved: if the profile's phone is in the list and it isn't already `admin`, it's promoted on that login. Deploy-time config, not client input — can't be exploited the way a user-writable `role` field could be. **Bug found re-verifying this live on 2026-08-19**: the 2026-08-18 verification only checked the token issued directly from `verifyOtp()`, never the real app flow — which immediately calls `PATCH /auth/onboarding` next. `completeOnboarding()` unconditionally set `role: dto.role` (seeker/owner from the onboarding form), silently overwriting the bootstrap promotion back down on literally the next request. Fixed: onboarding now preserves an existing `admin` role instead of overwriting it, regardless of what the onboarding form submits. Re-verified live end to end this time: `ADMIN_PHONES=+919900222201` → OTP verify → `PATCH /auth/onboarding` with `{"role":"seeker"}` in the body → `GET /auth/me` still shows `role: "admin"`. A second endpoint, `PATCH /admin/users/:id/role` (admin-only), lets that first admin promote/demote others from then on, so `ADMIN_PHONES` is only ever needed once per deployment. It has a self-demotion guard (`AdminService.setRole()` rejects a caller trying to remove their own admin role, unconditionally — not "unless another admin exists," the simplest rule that prevents a lockout) — verified live: a bootstrap admin's own self-demotion attempt got 400 both before and after promoting a second admin; a non-admin's attempt to self-promote got 403; the bootstrap admin successfully promoted a second real account to admin.
- **Bug found and fixed during this verification, adjacent to the module: banning didn't immediately revoke sessions.** `AdminService.setBanned()` now also revokes every outstanding `refresh_tokens` row for that user in the same transaction as the ban — without it, a banned user's *existing* access token (up to 15 minutes) and refresh token (up to 30 days, since `refresh()` does check `banned` but only gets called when the client actually attempts a refresh) would keep working until something forced the check. Verified live: banned a test account → its still-valid access token still worked (expected, not re-checked per-request) → its refresh token was immediately rejected (`401`) → a fresh OTP login attempt for the same phone was rejected with "This account has been banned."
- **Verified for real on 2026-08-18, end-to-end through `apps/web`'s actual `/admin` routes** (not just curling `apps/api` directly): created and published a listing as one test account → confirmed it appeared in `/admin`'s queue via `apps/web`'s `/api/gateway/listings/admin/queue` → bulk-approved it via the same gateway path the queue page's UI calls → a second test account reported it via `/api/gateway/reports` → the report appeared on `/admin/reports` → confirming it reverted the listing to `pending`, verified by re-fetching as the original owner. Also verified `GET /admin/users` (non-admin 403, admin sees the full list including a `_count.listings` per user), `PATCH /admin/config/:key` (round-tripped `report_threshold` from `3` → `2` → back to `3`), and `GET /admin/analytics` (see honest-zeros note below).
- **Analytics reads honestly reflect what's actually tracked, not the full funnel root `CLAUDE.md` describes.** Only `listing_view` is written by any `apps/api` code path today (fire-and-forget in `ListingsService.findOne`). `signup`, `contact_tap`, `chat_started`, and `listing_created` all read `0` — not because the query is wrong, but because nothing inserts those event names into this backend's `events` table yet (`apps/mobile`'s `lib/analytics.ts` still writes straight to Supabase via the pre-pivot client, see `apps/mobile/STATUS.md`). The UI on `apps/web`'s `/admin/analytics` says this explicitly rather than presenting the zeros as if the funnel were simply quiet.

## Push module (`src/push/`, `src/push-tokens/`) — built and verified live against real Expo infrastructure

`PushService.sendToUser(userId, {title, body, data})` (`src/push/`) fetches every registered `push_tokens` row for that user and POSTs to Expo's push API (`https://exp.host/--/api/v2/push/send`) directly — no SDK dependency, `EXPO_ACCESS_TOKEN` is read from config but optional (Expo accepts unauthenticated requests for basic sending; the token only buys enhanced delivery receipts at higher volume). `PushTokensController` (`src/push-tokens/`) exposes `POST /push-tokens` (auth-guarded) so a client can register a device — upserts on `(userId, expoPushToken)` so re-registering the same token on every app launch never creates duplicates.

Wired into both places that already write a `Notification` row, so push rides along with the exact same trigger: `ChatService.sendMessage()` (title "New message", body = the message text truncated to 120 chars, `data: {type: 'new_message', conversationId}`) and `ListingsService.notifyOwner()` (title "Listing approved"/"Listing rejected", `data: {type, listingId}`). Both fire-and-forget — a push failure never affects the request it rides along on, matching every other notification write in this codebase.

**Verified for real on 2026-08-19** with a deliberately fake token (`ExponentPushToken[fake-test-token-123456]`), specifically to prove the integration hits Expo's actual service rather than silently no-op'ing: registered it for a test account → sent that account a chat message → the log showed `Expo push ticket error for user ...: DeviceNotRegistered` — the exact response Expo's real API gives for an invalid token (confirmed independently by curling `https://exp.host/--/api/v2/push/send` directly with the same payload shape and getting the identical error). Repeated for the listing-approval path with the same result. Expo returns HTTP 200 for the batch call itself even when individual tokens are bad (errors are per-ticket inside the response body) — `PushService` parses that and logs per-ticket errors rather than only checking the HTTP status, which would have missed this entirely.

- **`apps/mobile` got the client-side registration call this pass** (`usePushRegistration()`, `src/features/notifications/pushRegistration.ts`, wired into `(tabs)/_layout.tsx` — the root of the authenticated area, so it runs once per signed-in session) — but it's **not testable end-to-end in this environment**, for two independent reasons, both checked and handled gracefully rather than left to throw: Expo Go removed remote push entirely on Android SDK 53+ (the same limitation that crashed app launch earlier this session, guarded here with the same shared `isExpoGo` check), and `EAS_PROJECT_ID` (required to mint a real push token) is still the placeholder value from `.env.example`. Once a real dev/production build exists with a real EAS project, this should just work — the server side is already proven live.
- **Not built**: auto-pruning a token once Expo reports it `DeviceNotRegistered` (the error is now logged and visible, not acted on — a user who uninstalls the app keeps a dead row in `push_tokens` until it's cleaned up some other way), and `apps/web` intentionally has no push client at all — root `CLAUDE.md` is explicit that web has no push, which is exactly why its in-app notifications center (built earlier this pass) matters more there than on mobile.
